The Original Code is Genesis3D

That line sits at the top of most files in the engine, followed by a date: released March 25, 1999. Version 1.1 followed that November, and community maintainers kept the source lineage moving for years. A new native Linux runtime now builds on that preserved work. This is how it happened.

It started because I wanted to tweak an old game

Not a project. Not a plan. I was playing something old and I wanted to change it, the way you do when a game is nearly right and you can see the one thing you would move. That question turns into a different question fast: what is this actually built on, and can I get at it.

Genesis3D is what I found: the published engine source, not a decompilation or reconstruction, preserved with later community maintenance and the original developers' comments still visible. Its Windows runtime could not run natively on the Linux machine in front of me.

So the tweak became the port. I worked on it with assistance from Gemini and Codex Sol, and the public Git history records the resulting changes.

1999 is still in there, and it talks

Published engine source was unusual. Eclipse Entertainment made the Genesis3D source available, so what survives is not merely a summary of how a late-1990s engine worked. It includes working notes from the people building one, mid-thought.

In Actor/body.c, someone is trying to work out lighting behaviour across the hardware of the day and gives up mid sentence:

point light and directional light don't seem much different, but in powervr they are... hhmmm...

PowerVR: unmistakably the hardware landscape of the period. In World/Trace.c, in the middle of the BSP traversal, someone knows exactly what the better version looks like and writes down why they are not doing it: the stack based approach could bail out early, but it's way too ugly. Two lines up: bsp ordering makes the magic happen. And in the OpenGL driver, at shutdown, a comment explains a glFinish by saying they are closing up shop.

The first two comments remain in modules used by the native build. The third survives in the historical OpenGL driver, which the Linux target preserves in the repository but does not compile.

The logo they made impossible to remove

Open Engine/Logo and the folder is its own time capsule: CORONA.c, streak.c, electric.c, A_CORONA.c, A_STREAK.c. Lens flares and electric arcs, compiled into the engine, for the animated splash that played before your game did.

Next to them sits poweredby.c. Its main payload is one array: unsigned char Poweredby_bmp[], a 256 by 256 bitmap whose 65,656 bytes are written as comma-separated integers in C. Beside it, WebUrl.c does the same thing again for the words www.genesis3d.com.

They were not being careless. The licence requires the original animated logo to appear first in a distributed product, demo, or application and requires the logo on marketing. Embedding the artwork in source made the requirement difficult to overlook. Twenty-seven years later, that decision is why the badge at the bottom of this page is not a redrawing of the Genesis3D logo. It is the original bytes, lifted straight back out of the array.

Four renderers, and one file that ruined it

Here is the part that decided whether any of this was possible.

The preserved Engine/Drivers tree holds four rendering backends: Direct3D, Direct3D 7, a wireframe debug driver, and OpenGL. In 1999, on Windows, the commercially sensible move was to pick Direct3D and commit everything to it. Eclipse instead defined a driver interface, put every renderer behind it, and shipped an OpenGL implementation alongside the Windows-focused alternatives.

The same instinct runs through the rest of it. The world is a BSP tree with precomputed lightmaps. Characters are actors with skeletal animation, held apart from world geometry. Collision is a swept hull query against the BSP rather than anything bolted to how a frame gets drawn. Simulation is kept separate from presentation. Every one of those is a seam, and seams are what let a stranger work on one part without detonating the rest. That is what publishing your source actually demands of the architecture.

And then, inside the old OpenGL driver, next to the rendering code, sits a file called Win32.c. The driver interface was modular, but the shipped host integration was still Windows-specific.

The engine could change graphics backends. But the shipped host path still ran through Windows: the window, message loop, input, timer, and the surface it drew into. Genesis3D was portable in the layer everyone worries about and tightly coupled in the layer people often forget. The native port therefore had to replace the host window, input, timing, and active rendering bridge while preserving the engine interfaces and behaviors exercised by the native tests.

The handover you can count

The licence identifies Genesis3D original code released on 25 March 1999 and attributes it to Eclipse Entertainment. Contemporary reporting records WildTangent's acquisition of Eclipse technology in October 1999, and the preserved repository identifies Genesis3D 1.1 as released by WildTangent on 15 November 1999. The technology was combined with WildTangent's Web Driver work.

The handover is visible in the source headers, but the current tree is not a pristine 1999 time capsule. Its Git history labels the 1.1 import and a sequence of later community snapshots through 2009. The current branch also carries the 2026 Linux changes. That lineage matters: Kadaken is publishing a port of inherited and community-maintained code, not claiming authorship of the original engine.

The public source used here is distributed with the Genesis3D Public License v1.01. The Reality Factory repository preserved later community work, and this port retains that provenance rather than presenting the code as newly authored from scratch.

Sources: the public Reality Factory Genesis3D history, the Genesis3D Public License, and contemporary acquisition reporting.

Games that shipped with Genesis3D

Genesis3D was used beyond demos and hobby projects. Documented commercial releases include the Windows shooters Extreme PaintBrawl 2 (1999), Catechumen (2000), and Ominous Horizons: A Paladin's Calling (2001). Historical game catalogues also identify the recognizable licensed game Dragon's Lair 3D: Return to the Lair (2002) as a Genesis3D title; it shipped on Windows and consoles.

These examples describe the engine's history; their games, names, and assets are not included in or licensed by this port. See the MobyGames Genesis3D catalogue and the individual historical records for Catechumen.

What runs today

The old Windows-hosted driver implementations are excluded from the native target. A new SDL2/OpenGL frontend loads the retained world and actor structures and submits their BSP faces, textures, lightmaps, and posed actor geometry to OpenGL.

  • SDL2 owns the window and input. The Win32 message loop and its per driver platform glue are gone.
  • Tested swept BSP collision. Automated real-map fixtures cover gravity, jumping, stairs, slopes, wall sliding, and ceiling rejection; final feel still needs wider hands-on testing.
  • Simulation pinned to 60 Hz. Actor motion and light styles advance on a fixed clock, whether the frame is presented at 60 or 120 FPS.
  • Lightmaps updated in place. Only dirty, visible tiles are re-uploaded. Geometry is never rebuilt.
  • Checked shutdown paths. SIGINT and SIGTERM release engine-owned graphics, world, and file resources under the documented sanitizer tests.

A 3D engine is one of the few kinds of software that genuinely rots. It sits on graphics APIs, operating systems and hardware assumptions that all move without asking. When they move far enough the code stops being software and becomes a document: readable, studied, not runnable. This branch turns that preserved code into a working native Linux runtime while keeping the original asset formats and core subsystems available for further work.

Come break it

This is the part I actually care about. The licence Eclipse wrote was designed to pull people in, and the whole point of getting the engine running again is that other people can now get at it.

Build it. Test it. Change it. Run it on hardware I do not have. Tell me what breaks on NVIDIA, Intel, Wayland, or a distribution I have never installed. The repository contains source but no legacy game assets, so runtime testing requires compatible assets you are legally entitled to use.

If you want something concrete, the community roadmap lays out six areas with real work in each: reproducible builds and CI, renderer completeness, platform coverage, audio and gamepad support, the asset and authoring pipeline, and parser fuzzing. It also says plainly what is out of scope, because Genesis3D is an engine and weapons, levels and game balance belong to whatever gets built on it.
